# Save identity reader and diagnostic follow-up

Routine native-save observations still read fresh on-disk content and retain the SHA256/SaveTime identity contract. UDS does not infer identity from file length or timestamps alone, does not change Duckov saves, and does not cache an unverified fingerprint across saves. The coordinator continues rejecting a snapshot when creation time, write time or length changes during the read. Same-slot reopen, replacement/restore detection, save intent, persistence retries and profile formats retain their existing behavior.

`NativeSaveFingerprint` hashes a buffered stream while extracting the small native UTF-8 SaveTime entry. The normal path avoids seeking back through the entire file and allocating a full-file UTF-16 string. A bounded 4 KiB timestamp candidate handles split tokens; unusual encodings, larger entries or ambiguous candidates use the original full-text parser semantics. Missing timestamps remain unavailable, never fabricated. The 64 KiB read buffer is pooled and returned on failure as well as success.

On Windows the reader calls OS SHA256 through CNG because the inspected Duckov Mono `SHA256CryptoServiceProvider` wraps `SHA256Managed`. Hash resources are released on every exit. If the native provider is unavailable or rejects the operation, the reader rewinds and uses the existing managed SHA256 algorithm. This adds no redistributed DLL; `bcrypt.dll` is loaded only from the Windows system directory. The API contracts are documented by Microsoft: [BCryptCreateHash](https://learn.microsoft.com/en-us/windows/win32/api/bcrypt/nf-bcrypt-bcryptcreatehash) and [CNG algorithm pseudo-handles](https://learn.microsoft.com/en-us/windows/win32/seccng/cng-algorithm-pseudo-handles).

The local diagnostic variant adds observation-only Harmony scopes around the installed `SavesSystem.CollectSaveData()`, `SaveFile(bool)`, `CreateBackup()` and `CreateIndexedBackup(int)` methods. These scopes include game work and other event subscribers; they must not be summed with nested UDS measurements or labelled as UDS-only cost. Void finalizers leave native exceptions unchanged. Missing contracts disable the probe with a diagnostic message, and patch cleanup uses the existing retryable Harmony owner cleanup. These probes are absent from the ordinary build.

The diagnostic variant also records bounded per-Update sampling windows in which process-wide GC collection counts increased. These windows give correlation bounds, not GC pause durations, allocation ownership or proof of causation. Separate generation counters may describe the same collection. Probes allocate no per-Update objects and report overflow; F9 resets and F10 ends the capture. Logging occurs when the summary is requested, not on each sampled frame.

The 2026-09-13 user-controlled 74.077-second diagnostic recording contained ten native-save callbacks with no dropped timing samples. Against the prior 70.397-second SQLite session, average UDS save-callback time fell from 23.5698 to 10.3943 ms and average save-identity time from 14.4355 to 2.8955 ms. The user reported noticeably smoother vendor/crafting interaction. These are different interaction sessions, not a controlled UDS-disabled comparison. Six Update intervals exceeded 100 ms (maximum 250.2338 ms). One included 106.2127 ms of Duckov indexed-backup work; other gaps remain unassigned or coincide with collection-count changes whose pause duration and ownership are unknown. All three retained run payloads matched the original data, crafting totals advanced, and both databases passed integrity and table-content comparisons after clean shutdown.
