# Structured Equipment presentation evidence

Schema 18 adds prospective metadata alongside the existing equipment duration aggregates. `EquipmentCompositionEvidence` belongs to every `EquipmentStatisticsAggregate`: the active run/checkpoint, route segments, completed runs, starting/route maps and lifetime. Clone and merge preserve it; reset starts a new empty instance. No new lifecycle hook, raw snapshot journal or per-frame history is added.

`Loadouts` holds one definition per exact LoadoutId: observed occupied/empty roots, stable item IDs and kinds, captured nested paths/states, names and root/nested completeness. Unavailable whole-set identities never register a readable subset. Compatible nested evidence and display names enrich metadata. Contradictory definitions permanently mark that identity conflicting; consumers must withhold its composition. Metadata is not a second duration counter. Additional legitimate native/modded roots remain present.

`ActiveTotemSets` holds only proven-active members under the existing TotemSetId. The existing identity deliberately excludes direct slot attribution. `TotemStates` independently retains carry kind, item, container, actual direct slot when observed, activation, copy ordinal and checked duration. Identical copies retain separate ordinal counters, representing copy-time rather than invented individual-object identities. Tote presence remains Unknown activation. No human-readable description or attachment hash is parsed.

The installed `ItemStatsSystem.Items.Slot` contract has public `requireTags` and a stable `Key`; its `DisplayName` is localized and is not classification evidence. `Duckov.Utilities.Tag` derives identity from the asset name. A sole required tag named `Totem` proves the slot category independent of its display name or ordering. Native capture records that proof. Only explicitly read Empty roots with this proof add `EmptyDirectSlots` duration. Unclassified slots remain unavailable for this specific value; historical empty time is never retroactively attributed using a later observation. Direct totem presence retains the unchanged `duckov:character` ContainerId plus a separate actual `DirectSlotId`.

The current-schema recovery validators reject missing collections, inconsistent root/nested definitions, wrong identity keys, invalid activation/copy state and nonfinite or negative durations before candidate selection. Exact native-prefixed definition IDs are checked against the structured canonical identity, without reversing hashes. Conflict markers remain explicit unavailable evidence. Existing backup/temporary candidate selection and interrupted completion carry the new data through the common equipment clone/merge path.

Development schema migration advances profile/statistics ownership from 17 to 18 without rewriting old per-run schema provenance or fabricating membership. Missing historical composition and typed presence are marked unavailable. Existing pre-v1 migrators remain through M17; this is best-effort development continuity, not a supported upgrade guarantee. Schema-17 terminal equipment remains its own independent evidence.

JSON includes the same structured data in every exported equipment scope. Dedicated `loadout_definitions.csv`, `active_totem_set_definitions.csv` and `totem_state_durations.csv` retain stable identity, root/path/state/completeness, direct/tote/activation distinctions, copy ordinals and duration. Definition headers explicitly identify Unavailable or Conflict history; missing composition cannot appear as a proven-empty set. The export set contains one JSON and 36 CSV files.

Deterministic Equipment composition, native snapshot, persistence/recovery and export tests qualify data behavior. Native gameplay and visual/audio qualification are separate user-controlled checks.
