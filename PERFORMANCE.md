# M8.1 performance protocol

This document freezes the M8.1 native benchmark method before runtime corrections are selected. Raw captures and their machine-specific sidecars live under ignored `artifacts/performance/captures/`; accepted results and hashes are summarized in `TESTING.md`.

## Capture method

- Collector: installed CapFrameX `1.8.6.2`, using its loopback capture API and bundled PresentMon. NVIDIA FrameView SDK `FvSvc`, OCAT, FrameView, and every other PresentMon-based collector must be stopped. CapFrameX sensor logging must be Off. Its overlay must be effectively unavailable or disabled: this machine has no RTSS installation or process, so the UI's configured `Overlay: On` state cannot render an overlay and is accepted only while that absence is reverified and recorded.
- Wrapper: `scripts/capture-frame-times.ps1`. It targets the one running `Duckov` process, verifies CapFrameX/API/process/settings state plus actual `Mod Loaded:` and UDS activation evidence from the current launch, refuses to overwrite evidence, and requests an explicit `JsonCsv` capture. Each accepted run preserves the raw CapFrameX CSV, raw CapFrameX JSON, and a `.capture.json` control sidecar.
- CapFrameX request: process `Duckov`, 10-second focus delay, 30-second timed capture, explicit `JsonCsv` output, an isolated staging directory, and a unique configuration/build/scenario/run comment. The wrapper validates the returned process, comment, one-run structure, and raw `MsBetweenPresents` rows before publishing the three artifacts.
- Analyzer: `tools/FrameTimeAnalyzer`. It accepts either the wrapper's raw PresentMon CSV or CapFrameX's native `.capframex.json` raw arrays. For CSV it requires a raw frame-time column, skips CapFrameX's leading `//Ignore=true` marker, excludes dropped rows, selects the dominant swap chain, and prefers CapFrameX's `CPUStartQPCTimeInMs` clock for correlation. Native JSON uses CapFrameX's already-selected run arrays (`MsBetweenPresents`, relative `TimeInSeconds`, `CpuActive`, `GpuActive`, and `Dropped`) and rejects missing, multiple-run, or length-mismatched evidence. Both paths report individual captures, isolated action windows, optional named time windows, and the same distributions and spike rules; controlled cells aggregate medians of per-run metrics rather than concatenating captures. Optional raw CPU/GPU-busy distributions are diagnostic evidence for CPU-versus-GPU isolation; release gates remain based on presented frame times.
- Quantiles: linear interpolation at `(n - 1) * p`. Average FPS is `1000 / mean frame time`; acceptance is based on frame times rather than the Steam overlay.

The schema-5 sidecar records the exact CapFrameX executable/version/hash, API request/response and relevant settings, both raw-artifact hashes, Duckov/game build, process start, repository commit, deployed package hashes, Harmony version/hash, active mods, save generation, route/association state, controlled background-application state, action kind, weapon/ammunition, complete equipment/totem state, action window, graphics preset, resolution, display mode, refresh rate, frame limiter, and V-sync state. Consumable captures additionally require the exact consumable, use/count expectation, starting HP, active damage-effect state, and passive-healing state. Requested action offsets are distinct from the request-relative UTC/stopwatch offsets of every audible signal, and CapFrameX API response latency is recorded; the analyzer uses the observed signal offsets. It also records that ordinary hydration/energy decay is accepted rather than pretending those continuously changing survival timers can be frozen. The wrapper fails before capture when any required material control is blank or a known placeholder. Earlier sidecars remain immutable evidence but cannot prove controls added after their creation.

## Matched controls

Use cold Duckov launches and the same save slot/generation, route state, location, facing, weapon instance, modifications, ammunition, magazine/shot count, graphics settings, display mode, resolution, refresh rate, frame limiter, V-sync, background-application state, duration, action timing, and collector flags. Exclude loading, menus, inventory management, route transitions, unrelated movement, and active injury/status changes. Natural hydration and energy decay is allowed: it occurs continuously, the user identified it as non-material for these stationary sequences, and the clean-A per-run medians remained stable across the decay. Keep cell order and elapsed timing reasonably consistent, but extract whenever needed to protect the retained weapon and character. Record any other condition that cannot be held constant before deciding whether a run remains valid.

Each acceptance cell needs at least three valid captures. Calculate each run independently and take the median of its run-level result. Keep invalid captures and record the objective invalidation reason; an inconvenient result is not an invalidation reason.

The standard 30-second firing capture has five stationary pre-action seconds, a frozen scenario-specific action window, and stationary recovery through capture end. Signals mark capture start, action start, action end, and capture end. The primary MP7 pilot uses one 30-round magazine and an action window from seconds 5 through 8: fire continuously at the action-start signal until empty, then remain still; the low signal closes the correlation window. The raw pilot determines whether that three-second window safely contains the full firing phase before acceptance timing is frozen. Acceptance captures use the same recorded shot/magazine sequence and action timing for every matched configuration.

After the matched D/B matrix is complete, one supplementary production-D soak records an entire natural run across at least three sequential map loads. This is deliberately not another matched acceptance cell and cannot replace or weaken the frozen D/B ceiling. On the installed CapFrameX 1.8.6 UI, the user sets capture time to `0` (unlimited), leaves sensor logging Off, starts and stops the record with one deliberate F11 press at each boundary, and retains the native JSON because that UI exposes no JSON+CSV option for manual capture. Codex does not launch or control Duckov. The untrimmed record includes route transitions and loading; the report separately names the actual raid interval, each native run segment/map interval, and equal early/middle/late raid slices by aligning CapFrameX's logged capture-start UTC with its raw relative clock and authoritative UDS UTC lifecycle timestamps. The JSON `Info.CreationDate` is completion-time metadata and is not misrepresented as capture start. Natural movement, combat, weapon swaps, survival decay, and any adverse result remain in evidence. The user reports perceived hitches only after stopping the capture so observation does not add mid-run focus stalls.

The soak-discovered Med-Kit correction uses a separate matched `consumable-medkit` cell. Run Harmony-only B before deploying the hardened D candidate, with one cold launch per configuration and three valid 30-second captures in the same safe Nullpunkt area. ## Static audit before the pilot

The complete M1-M8 production trace established hypotheses to measure, not permission to optimize before the native control:

- M4's accepted firing callback constructs identities, display names, integrity state, event capabilities, and an equipment association, then reduces weapon and equipment statistics into both the active run and current route segment.
- M5 correlates every projectile at initialization and patches private `Projectile.Update`. Every live correlated projectile therefore enters and exits an ambient Harmony scope on every frame, including empty-space flight. The installed 2.3.30 assembly performs its raycast and calls `DamageReceiver.Hurt` inline in that private update; no narrower native hit event was found.
- Projectile completion emits accuracy evidence and performs the same run/segment combat fan-out. Every `Health.Hurt` prefix captures an equipment association before actual HP loss or target relevance is known; an actual transition then resolves identities/cause and reduces combat/equipment statistics into run and segment scopes.
- M6's equipment association provider synchronously rebuilds the complete equipment/totem snapshot. A build sorts slots, traverses and hashes attachments, scans tote contents, builds loadout/totem/snapshot identities, and publishes the observation. An unchanged observation still advances and clones current equipment state in both run and segment aggregates. Accepted firing plus projectile initialization can therefore request at least two complete equipment observations per projectile before any hit.
- M8 adds source/outcome segment association and doubles applicable weapon/combat/equipment reducers into current route-segment aggregates. Association recording also searches retained segments before appending bounded evidence.
- Dirty firing/combat mutations no longer write once per event. The scheduler permits a growing active-run clone, validation, JSON serialization, disk flush, and atomic replacement at a bounded one-second cadence, plus transition/terminal/shutdown safety flushes and bounded retry. This remains a possible periodic hitch rather than a per-shot write.
- The raid UI does no layout work while hidden; its per-frame tick only checks the hotkey. Combat Harmony patch-set reflection runs at a two-second conflict-check cadence. Ordinary firing/combat paths do not log per event.

History locates the cumulative cost windows without assigning blame: firing statistics entered in M4, projectile/update/health attribution in M5, equipment association in M6, and route fan-out in M8. External A/B/C controls and, only if needed, the opt-in counters decide which costs are material.

## Metrics and acceptance

For every capture report duration, frame count, average FPS, mean, median, p95, p99, maximum frame time, counts and percentages above 8.33/16.7/33.3 ms, every >33.3 ms offset, whether the spike occurred during the action window, dominant/non-dominant swap-chain rows, and warnings. For action scenarios, independently report the frame count, summed frame duration, average FPS, median, p95, p99, maximum, and threshold percentages for only the frozen action window; whole-capture medians must not dilute the firing phase.

Primary comparison is D versus B. Secondary comparisons are D/A, D/C, and B/A.

- Engineering target: D/B median frame-time overhead at most 5%, p99 overhead at most 10%, indistinguishable >16.7 ms rate, and no UDS-specific >33.3 ms frame or cluster.
- Maximum ceiling: D/B median overhead at most 10%, p99 overhead at most 20%, no repeatable increase above 16.7 ms greater than 0.25 percentage points unless raw evidence proves unrelated noise, and no repeatable new >33.3 ms cluster.
- Cluster: at least two >33.3 ms frames within a rolling one-second window during the same practical firing phase, present in at least two of three UDS-enabled captures and absent from corresponding controls.

A single isolated maximum outlier is diagnostic rather than an automatic failure. One repeatable weapon/scenario failure rejects the candidate even if aggregate averages pass.

## Measured diagnosis and hardening

The accepted A/B/C controls isolate a CPU-side UDS regression. Harmony alone remains indistinguishable from the clean control, while production v0.8.0 fails the matched B ceiling at idle p99 and at high-rate empty-space firing p99 and material-frame rate. The opt-in counter build then established exact production-boundary frequency rather than relying on source shape alone:

- A 30-second idle interval performed 150 complete equipment builds, 260 reflective patch-set inspections, and six full checkpoint clone/store operations despite no gameplay input.
- One matched 30-round empty-space interval performed 30 firing reductions, 30 projectile captures/completions, 348 per-frame projectile scopes, 60 equipment-association requests, 213 complete equipment builds, 272 patch-set inspections, and eight checkpoint clone/store operations.
- No health transition occurred in the empty-space interval. The firing interval therefore isolates hot work before enemy identity, damage, kill, or hit fan-out is added.

The v0.8.1 correction keeps every accepted event and attribution but changes where repeated work occurs:

- Public slot, hold, inventory, and item-tree events immediately refresh an immutable equipment snapshot. Firing and projectile associations read that event-time cache instead of rebuilding and republishing the entire attachment/totem tree. A one-second watchdog reconciles missed external mutations without defining normal event timing. Unchanged snapshots are not republished within the same segment, but the same immutable loadout is published once after every segment change so segment-local equipment roots remain complete. If route context becomes unavailable, the adapter publishes one stable overall-only observation instead of suspending equipment: overall duration and event-time associations continue, while only route-dependent evidence degrades.
- Healing, combat, and container patch sets still receive full ownership validation at activation. UDS then captures the reference identity of Harmony 2.4.1's serialized shared-state token for each original method. Every subsequent patch or unpatch replaces that token; runtime integrity checks therefore require only a locked dictionary lookup and reference comparison, distributed across the existing two-second cycle. Healing effect/health/buff callbacks perform the same stamp check at the callback boundary. A changed, missing, or inaccessible token conservatively disables the dependent capability; no runtime check deserializes patch metadata, launches background reflection, or weakens conflict detection.
- Projectile generation/run/map context is synchronized once per Unity frame while correlations exist. Ambient scopes retain direct reference identity and health processing reuses the application-time association already carried by the active scope.
- The main thread still creates the exact immutable active-run checkpoint at the existing one-second dirty/five-second periodic cadence. Validation, JSON serialization, durable flush, and atomic replacement execute as one single-flight background write; lifecycle, profile, transition, terminal, export, and shutdown boundaries wait for it. A captured mutation revision prevents an older completion from clearing newer dirty state, and failed writes remain visible and retryable.

Deterministic tests prove cached association identity across 60 reads, immediate event invalidation, the watchdog bound, complete non-burst stamp coverage, patch-state change/missing-state/owner rejection, zero managed allocations across 10,000 trusted stamp checks, nested reference-scope unwinding, single-flight checkpoint submission, exact-value persistence, failure surfacing/retry, non-consuming waits, and post-snapshot dirty-state preservation. Final acceptance still uses configuration D with ordinary production diagnostics and the complete feature set; none of these structural proofs substitutes for the matched native matrix.

## M9 Economy preservation note

M9 does not modify the accepted firing, projectile, health/combat, equipment, Harmony-integrity, or native diagnostic paths measured above. It adds lower-frequency public economy callbacks and one ordinary-frame `economyAdapter.Tick()` call. A clean tick returns without reading the Money balance, traversing an inventory, cloning a profile, or touching disk. Generic storage/main/pet/item callbacks set one dirty flag and coalesce into one owned-Cash scan; completed pickup, sale, and cost boundaries may flush that scan immediately so opposing transactions are not merged into an inferred semantic result. Full-scene inventory hydration suspends Cash reconciliation from level-initialization start/economy load through `OnAfterLevelInitialized`; callbacks during that window perform no owned-item scan, and the completed loaded inventory becomes one non-economic baseline. One ordinary scan deduplicates overlapping storage/main/pet enumeration by runtime item identity before summing and treats conflicting counts for one identity as contract failure rather than guessing. Pending Money correlation is bounded at 512 and over-capacity deltas publish exactly as unknown. Economy transaction identity metadata is constant-size: a directly recording aggregate stores one producer activation ID and one closed-through sequence, including a valid registered sequence-zero state before the first event. Recording and cloning are O(1) in historical transaction count, and completed-run fan-out copies exact totals without transaction IDs.

The M8.1 single-flight checkpoint/profile architecture is reused. Every accepted economy mutation, including Base and Shop flows outside a run, dirties the profile snapshot writer instead of synchronously replacing the profile per event; active-raid mutations additionally dirty the existing checkpoint revision and retain the exact lifetime recovery watermark. Transition, terminal, export, profile-change, scene-initialization, and shutdown barriers drain pending economy evidence before reset and retain checkpoint-before-profile ordering. ## M10 lossless-association engineering and qualification plan

The M10 production-path audit found five writers to the shared route-association surface: firing, combat, container access, item use, and healing. Their run and segment reducers already own the exact statistic totals; the schema-8/9 raw association list was retained only for event-attribution evidence, validation, UI/export projection, and route-capability provenance. M9 economy is deliberately absent from this surface and continues through its independent cursor-deduplicated run/segment fan-out. Delayed combat and healing retain distinct source and outcome segment identities. Active checkpoints clone this route state on the main thread at the existing dirty/periodic cadence, then the single-flight writer serializes it off-thread; retaining an unbounded raw list would therefore grow both every snapshot clone and persisted payload with completed event volume.

Measured schema-9 checkpoint JSON grew from 4,583 bytes with no association rows to 457,190 bytes with 2,048 rows, approximately 221 bytes per completed event and roughly 22 MB at 100,000 rows before legitimate statistic growth. M10 instead stores one exact bucket for each observed event-family/source-segment/outcome-segment key. Recording is an indexed lookup using a value-type key and checked `Int64` increment; it performs no full-history scan, no per-event durable write, and no concatenated-key allocation. Current schema-10 state is bounded by five event families and at most 64 by 64 valid source/outcome pairs, while the legacy schema-9 list remains capped at its already finite 2,048 rows. Deterministic tests prove the serialized checkpoint size after 100,000 repeated accepted events remains within 256 bytes of its 10,000-event size once bounded duplicate-ID windows are full, and stays below 200,000 bytes. The counters and timestamps change; the row cardinality does not scale with completed event count.

Because the changed recording path is exercised by high-rate firing and combat as well as lower-rate item/healing publication, the initial matched-control subset is the frozen M8.1 Electrified MP7 empty-space cell (three Harmony-only B and three enabled D captures), Electrified MP7 single-enemy cell (three B and three D), and Med-Kit cell (three B and three D). Whole-capture and action-window results must be analyzed from the same captures. One user-controlled three-map candidate soak supplements the matched cells with transition, persistence, and perceived-smoothness evidence. The matrix expands only if this subset is ambiguous, breaches a median/p99/spike threshold, or exposes a changed production path not exercised by those cells. Automated structural proof is necessary but does not close this live performance gate.
